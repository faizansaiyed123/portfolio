    The pipeline, step by step

    1. Ingest in the background

      Uploads and URLs are processed by a worker, off the request path. PostgreSQL is both the database and the job queue, so there is no Redis to run.

      app/services/knowledge.py ↗

    2. Chunk with structure

      Text is split into chunks that keep their heading path, so answers can point back to a section.

      app/services/chunking.py ↗

    3. Embed and store

      Chunks are embedded (384 dimensions) and stored in pgvector next to their text.

      app/ai/embeddings.py ↗

    4. Hybrid retrieval

      Vector search and Postgres full-text search run separately, then merge with reciprocal rank fusion (k=60). Every query is scoped to the caller’s organization and to documents that finished processing.

      app/services/retrieval.py ↗

    5. Rerank

      A cross-encoder rescores the candidate pool. If the reranker fails, the system falls back to the fusion order instead of failing the request.

      app/ai/reranking.py ↗

    6. Grounded generation with citations

      Retrieved text is labeled untrusted reference material in the prompt. The model is told to answer only from it, and the cited chunks are saved with the answer.

      app/services/rag.py ↗

    7. Evaluate

      Recall@k, mean reciprocal rank and a lexical groundedness check, chosen over an LLM judge so the model is not grading itself.

      app/services/evaluation.py ↗

    Design decisions and limits

    • PostgreSQL as the queue keeps one system of record. The cost is a single-host design.
    • The model runs locally in Ollama behind a provider interface, so a hosted model can replace it.
    • The rate limiter is in-process, so it is correct only for a single API process.
    • Ollama is not horizontally scalable, so real concurrency needs a hosted or dedicated model service.
